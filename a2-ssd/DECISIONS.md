# A2 SSD Platform — build decisions (Opus 5.5 build window, 27 Sep 2026)

Each line: the call, why. SPEC §12 and the accepted prototype win over earlier SPEC sections.

D1 · Worktree ~/Sites/ols-wt-a2 on branch a2-ssd-build (from origin/main 05ee12d). The main checkout stays on its own branch so no other window is disturbed (standing rule: leave other windows' folders alone). Never under /tmp.
D2 · The repo is PUBLIC (gh: visibility PUBLIC). Anything in it is on github.io. So the answer-bearing sources — judge/ (judge.js, markpoints.js, twinpoints.js, controls.js) and the content with models (papers.json model/msPoints, twin models) — live PRIVATELY in "Claude Work/A2 SSD Platform/src/" (the KS3 content-src pattern). The repo a2-ssd/ holds seeds, tools, gates, the public content the packer emits, the platform and the server. First-actions step 4 was done literally (copied into a2-ssd/, 484 GREEN), then moved to src/ before any commit. Gates read src via A2SSD_SRC (default that path).
D3 · The judge runs on the server only. pack-content.js bundles judge.js + markpoints.js + twinpoints.js + every exam model + every twin model into one script, encrypts it with A2SSD_SECRET, and writes it into the server source as a string. Code.gs decrypts it once per execution (cached in CacheService per build) and evaluates it. The client never holds a detector or a model; Show the examiner's answer asks the server. Keystream: SHA-256(secret|file) once, then a pure-JS xoshiro128** stream (Utilities.computeDigest per 32-byte block would cost seconds per call on a 150 KB bundle).
D4 · Public content (papers without model/msPoints, mark-point labels + marks + habits, lessons, twin questions + tables, strings) is INLINED into the served page at build time, not fetched: one deploy = one consistent set, no CORS, no stale cache. The server stamps BUILD into the page; every call carries it; a mismatch answers `stale` and the page shows the SPEC §3.9 reload line. Seeds and sql.js are served from github.io (sql.js vendored into a2-ssd/platform/vendor).
D5 · Every pupil/teacher string lives in content/strings.json (from SPEC §3 and the accepted prototype, each with its source) or in the paper/lesson/twin content. Client code holds no pupil-visible literal. G4 enforces it.
D6 · Lessons carry per-step `need:[skill]`. A part's lesson shows only the steps whose skills its mark points use (a step with no `need` always shows). The worked statement is modelled as tagged lines and assembled at render; commas between fields are added structurally, so a hidden step never leaves a dangling comma. G1/G5 check each part's visible steps against its mark points.
D7 · CREATE splits in two lessons: CREATE (Tinies set 1, CHILD — name, fields, PK, NOT NULL, composite-key shape, FK) serves 2015-1, 2016-1, 2022-a; CREATE-RULES (set 2, STOCKORDER — IDENTITY, DEFAULT GETDATE(), NOT NULL, CHECK, FK) serves 2023-a, 2026-b, 2018-a. One shared aggregates lesson serves GROUP-COUNT and GROUP-SUM.
D8 · Twin tables re-targeted so no twin re-serves a lesson's worked table: T-CREATE-2 → ATTENDANCE (set 3), T-CREATE-3 → SESSIONBOOKING (set 4) (see F6).
D9 · The judge reads every script six ways (plain; quote repair; requote of bare values; both; SELECT aliases without AS; "double-quoted" names as identifiers) and each point takes its best reading. A punctuation slip therefore can never cost a mark while a content fault (wrong field, table, value, missing clause) still does, because no reading invents content. Bracket repair works on the statement's own words: a bracket is closed where the group's word says it ends (a type size, a key column list, GETDATE's empty brackets) and opened where a word needs one; the must-cost half of G1 proves the repairs never give content marks away.
D10 · G1 must-cost exemptions only where the CCEA scheme itself gives no mark for the thing removed: 2016-1 table name, 2016-2 FROM, 2019-c ORDER BY (GROUP BY also earns it). Each is written in g1-judge.js with its reason.
D11 · Answer-space controls (5 right / 5 partial / 5 wrong per mark point) are written by SEPARATED Sonnet readers from the verbatim CCEA scheme, never shown the engine (gates/answerspace/RULES.md, private). Every disagreement with the engine is adjudicated against the scheme: engine harsher → engine fixed + control; reader wrong → control corrected with the reason; note over-promises → note fixed. The adjudicated set becomes judge/answerspace.json and runs inside G1.
D12 · Expected rows are computed LIVE, never stored. Seeds date themselves from today, so a precomputed expected/*.json goes stale overnight (F13). The server's `mark` reply carries the model SQL for the paper ("turn") only, never for Another question; the client runs the shimmed model on a fresh copy of the seed to fill Expected rows and Same rows / Different rows. The model text is never displayed until Show the examiner's answer (showAnswer, which sets saw-answer). expected/*.json dropped.
D13 · G2 re-dates every seed by replacing 'now' with nine anchors (today, 2026-01-01, 01-31, 03-01, 03-31, 06-30, 09-01, 12-31, 2028-02-29): month ends, year ends, a leap day and a short month. Every SELECT model must return ≥1 row on each. "This month" rows use max(date('now','-N days'), date('now','start of month')); "last month" rows use 'start of month','-1 month','+N days' with N < 28.
D14 · The Tinies twin sets get their own seeds (seeds/tinies-1.sql … tinies-4.sql), table-for-table with twins.json, each with traps beside the rows the answer wants. Set 5 (DAYTRIP) is CREATE only: no seed; G2 builds its model on an empty database.
D15 · Every TEXT column is COLLATE NOCASE, so 'tinies 2' finds 'Tinies 2' as SQL Server's default collation does.
D16 · Papers with no GETDATE question keep their printed dates (2016, 2017); only date-relative questions get date('now', …) seeds.
D17 · Mark-scheme spellings that differ from the printed tables run as views: STAFF_SPECIALTY (2024), BOOKINGS (2025), SUPSTOCKORDERDETAILS (2026). Either spelling runs in SELECT; the DATA tab lists only the printed table.
D18 · The DATA tab hides whatever the part asks the pupil to make. pack-content derives `hides` from the model: CREATE → that table (2015-1 DIVE, 2016-1, 2018-a CONTRACT, 2022-a, 2023-a and 2026-b SUPPLIERSTOCKORDER); ALTER … ADD → that column (2024-c-i STAFF.StartDate).
D19 · Result grid headers copy SSMS: a column that is not a plain name or an alias shows "(No column name)" (FirstName || ' ' || Surname, COUNT(SalesNo)). Same rows compares values in order, never column names. G5 checks both.
D20 · Lookup tables keep their real size (2 sites, 4 areas); G2 asks for ≥1 row, not SPEC §6's "8–20".
D21 · The shim's DATEADD month/year clamps to the month's last day as SQL Server does (31 Mar − 1 month = 28 Feb; 29 Feb 2028 + 1 year = 28 Feb 2029), where SQLite's own modifier overflows into the next month.
D22 · Canonical copies: a2-ssd/seeds and a2-ssd/tools/tsql2sqlite.js in the worktree. The design folder keeps copies with a README pointing here.
D23 · Table prefixes: strict only inside a join equality (a prefix naming a table not in the FROM, or a field compared with itself, loses the join mark); everywhere else an unknown or wrong prefix is a slip and is dropped (ruling 13: prefixes never cost). A field followed by arithmetic (SET STOCK.Price = STOCK.Price * 1.1) is a calculation, never a join.
D24 · Field ownership (points saying "from two or more tables") follows D23: a known prefix names its table; a bare or slipped field belongs to whichever FROM table holds it; a partial answer with no FROM yet looks across the paper's tables, so it reads as far as it goes.
D25 · Rulings settled while running the six reader answer sets (gates/answerspace, 3,135 controls): LIKE with no wildcard = equals; LEFT JOIN where INNER is printed keeps the join marks (2016-2 rows are the same); INSERT without INTO and INSERT…SELECT keep the marks; two inline PRIMARY KEYs is not a composite key (0 with a note); a 2026-d ON condition without the alias keeps the mark with a note; COUNT counts a field of the right table or *; clauses in any order read; DATEDIFF(day…)=0 for "today" is right; 2024-d takes the strict forms MARK_POINTS lists (> 5, < DATEADD); TODAY + 1 stays right for 2021-b (MARK_POINTS line 242); a misspelt field name costs (it is a wrong field); a comma or semicolon in place of AND in a WHERE loses the pairing mark (it is a missing clause, not punctuation); a hard-coded past year in 2022-d loses the "this year" mark, the current year keeps it with a note. Each is in gates/answerspace/adjudicated.json (40 entries) with its reason, and G1 step 6 fails on any new disagreement.
D26 · 2025-b: the total may be SUM(Duration)/60, SUM(CAST(Duration AS …))/60 or CONVERT; ORDER BY must be the total hours DESC (ordering by the count loses that point). "Next week" = the 7 days from one week ahead, in any of the date forms MARK_POINTS lists.
D27 · Booklet mark lists (twins.json ms_marks) are now written FROM the judge's own point labels (twinpoints.js), one line per point with its marks, so the list a teacher reads and the marks a pupil gets cannot drift. Lines that no longer carry a mark: "VALUES keyword" (B-3a, B-4a), "FROM … with alias" (B-1d, B-2c, B-2d, B-4c) — an alias never earns or costs a mark (ruling 13).
D28 · Practice questions moved off tables and facts a lesson or another answer shows (adds to D8): T-INSERT-1 → CONTRACT; T-SELECT-2 → "this year"; T-COUNT-1 → "more than 3 in the last six months"; T-PROSE-2 → ATTENDANCE. His booklet already uses STOCKORDER/ORDERLINE (B-2b), so the INSERT lesson moves to SESSIONBOOKING (D34).
D29 · B-5a: a CHECK with no constraint name keeps the mark with a note; his booklet deducts 1. The papers never give a mark for a constraint's name, so the practice question does not either.
D30 · T-CREATE-1 has no "well-formed" mark; it is 6 marks, each one a thing the pupil wrote.
D31 · One consistent wrong value used on every row (B-2b order number, B-4a crèche) costs ONE mark with a note naming the right value, not every row's mark.
D32 · Follow-through: ORDER BY the pupil's own SELECT total keeps the ORDER mark (T-SUM-1); IS NOT NULL keeps "field tested for NULL" (T-LEFT-1); a wrong or misspelt INSERT table loses only the table mark (B-1a).
D33 · content/clusters.json maps every part to a skill cluster: the cluster names the lesson (lessonFor overrides: 2018-a, 2023-a, 2026-b → CREATE-RULES) and the practice-question queue (order[part], else the cluster's twins; the first one the pupil has not done). G1 step 8 fails a missing lesson or a practice question that re-serves its lesson's worked table.
D34 · The INSERT lesson (CLOZE-INSERT's neighbour, INSERT.js) works on SESSIONBOOKING, not STOCKORDER/ORDERLINE, which his booklet's B-2b already uses (D28).
D35 · Lessons sit on the Tinies set whose tables fit the skill: AGG-COUNT, AGG-SUM and AGG-WEEK on set 4; AGG-MONTH, PROSE-DESIGN on set 2; CLOZE-AVG, PROSE-KEYS, PROSE-JOIN, PROSE-CRITERIA on set 1.
D36 · The one aggregates lesson became six short ones, each teaching one thing the papers test: AGG-COUNT (COUNT with GROUP BY), AGG-SUM (SUM with ORDER BY the total), AGG-WEEK (a total over next week, Minutes field), AGG-VALUE (a worked value per row), AGG-DISTINCT (COUNT DISTINCT), AGG-MONTH (last calendar month). A part's lesson is named in clusters.json lessonFor.
D37 · A lesson grid can have variants per part (need/not/parts), be ordered, and hold tokens ({today}, {somIso}, the start of this month) that the client fills with the pupil's real date, so a grid is right on any day. The lesson gate runs every grid on nine dates (the G2 anchors) and rounds numbers to 6 places.
D38 · The detector (every lesson statement scores ≤ half on every part and practice question) runs over every statement variant, not just the first (F42). SELECT-JOIN's statement was changed so it no longer handed over B-4b.
D39 · "FROM and JOIN" is one step in every lesson: the join line is meaningless without its FROM.
D40 · Seeds changed so each lesson's grid shows the case it teaches beside a trap: tinies-2 (N0102 on four orders), tinies-3 (a four-hour session), tinies-4 (Minutes on each session; bookings across month ends). check_seeds.js is removed: G2 already runs every SELECT model on nine dates, and it pointed at a judge path that no longer exists. Expected results, if the client needs them, come from pack-content.
D41 · The practice-database converter: DATEDIFF(MINUTE/HOUR) counts real minutes (F43); DATEADD(MINUTE/HOUR) keeps the time (F45). Weeks count Sunday-to-Sunday boundaries as SQL Server does.
D42 · One wrong field inside COUNT costs one mark on 2022·d, not two (F44).
D43 · CLOZE-INSERT's statement gives the short name for the table in a note, because the cloze stub does; the note never names an exam field.
D44 · Cloze lessons: the construct blanks (keywords, functions, the short-name rule) are taught in full; the data blanks (which field, which value) are never given. A copied lesson cloze scores at most 1 of 4 or 5.
D45 · CLOZE-AVG's grids CAST the average to INT, because SQL Server's AVG of whole numbers is a whole number (696.25 shows as 696); the pupil's own query is not cast.
D46 · The written-answer lessons are four short lessons, one per kind of question, plus ALTER for 2024-c-ii: PROSE-KEYS (name the constraint, 2021-a), PROSE-JOIN (inner join's effect and the join that keeps every row, 2022-b-i/ii), PROSE-DESIGN (why a field sits in the link table, 2026-a), PROSE-CRITERIA (a criterion the list still needs, 2018-b-ii). They carry answer:'text': the statement is plain sentences, not SQL colours, and the lesson gate runs only their grids.
D47 · The detector for written answers: the lesson uses a different database, different fields and a different field-to-constraint order, so a copied lesson answer scores 0 on every prose part. PROSE-KEYS lists FOREIGN KEY, CHECK, PRIMARY KEY, so copied rows score 0/3; re-ordered by the pupil they score 2/3 on 2021-a and T-PROSE-2, because "it identifies each row" and "it must match a row in the other table" are the meaning of the constraints themselves. PROSE-JOIN (ii) names LEFT JOIN, which is the whole answer to 2022-b-ii and T-PROSE-3. Both are accepted exceptions: the answer is the construct, and mapping it to the exam's fields is the skill.
D48 · The lesson task for 2018-b-ii works in the Tinies database (the toddler list at Tinies 2) and teaches the method: look at every table the list uses for a field that makes a listed row wrong. It never uses the words year, within, between, start or end date.
D49 · Every part now names its lesson (clusters.json lessonFor), and lessons.json is regenerated from src/content/lessons/*.js by src/tools/build-lessons.js, never edited by hand.
D50 · G1 step 10 is the lesson gate (tools/g1-lessons.js), with ten planted faults that must each be caught. The detector's reach: an SQL lesson is scored against every SQL part and practice question, and blank by blank against every cloze (each run of words on a line of the statement tried in each blank); a written lesson against every prose, short and rows part. A piece the cloze question already shows (StartTime is in the stub's column list) or a lone digit (most statements hold a 2) hands over nothing and is not counted. An SQL lesson is not scored against written parts: a lesson that writes LEFT JOIN teaches the construct, the D47 reason.
D51 · 2022·d row 6 (HAVING COUNT(…) > 1) takes any argument inside COUNT; the field counted is marked once, in the SELECT (F44). Recorded in gates/answerspace/gen_adj.js.
D52 · src/tools/build-schema.js reads the repo's seeds (the canonical ones since D40), not the design folder's frozen seeds/. The schema did not change: D40 changed rows, not columns.
D53 · A field quick question may accept more than one field (NULL-OR: CONTRACTJOB.JobNo or JOB.JobNo): answer is then a list. The client accepts any of them.
D54 · The judge runs on the server. The private Code.gs (built into "Claude Work/A2 SSD Platform/deploy/", never committed) bundles schema, judge, markpoints, twinpoints, a models map (paper models with CLEAN overrides; practice-question mark scheme, worked answer and mark list) and clusters. The repo holds server/Code.gs.template with no answers. The page never holds a model or a test, so no secret or encryption is needed.
D55 · Written-answer rows labels that name the answer ("AnimalID: PRIMARY KEY, with the reason") are shown as "AnimalID: the constraint, with the reason" before the pupil is marked (F51). The judge's own label is used after marking.
D56 · Staff door: the class owner and the heads of department (Script Property hods) are let in by their signed-in school email, with no passcode. Other staff use a generated passcode, held only as a salted SHA-256 hash in the private Code.gs (a Script Property staffPasscode overrides it). The plain passcode is kept in "Claude Work/A2 SSD Platform/STAFF_PASSCODE.txt" (mode 600) and never in the repo.
D57 · A new class opens with 2015 only; its teacher opens more from the staff page. The class record is {o owner, c created, order, open}. The live grid marks the teacher's own row; the CSV leaves it out; the teacher can clear their own test record.
D58 · Storage: one record per pupil per class (p:<class>:<email>), each part holding door, first, best, attempts, seen, best-after-seen, practice question id and its first/best/attempts/seen, and flags. Scripts sit apart (d:<class>:<email>:<part>), each capped at 2000 characters. Drafts and lesson progress sit in the pupil's own UserProperties. A sweep archives the oldest finished papers to the Sheet "A2 SSD - Archive" when the store passes 350 KB; the served page never touches the Sheet.
D59 · The server marks: first attempt, best, attempts and the practice-question assignment are decided under the script lock, and a locked paper refuses a mark. The page never tells the server a score.
D60 · Another question: once assigned, a part keeps its practice question. None is needed when the pupil chose Write it now and scored full marks first time. Otherwise the first question in order[part] (else the cluster's) not met on any part; none when all are met.
D61 · The dev harness (tools/dev-server.js) runs the real assembled Code.gs in Node with Apps Script shims (properties per dev user, session, lock, userinfo, digest). G3 and G5 run against it.
D62 · A quick check's wrong pick shows wrong[picked] first, then outside, then the general line (F52).
D63 · Expected rows stay private. pack-content.js runs every paper SELECT model on its seed for each of 464 days (from today's build to A2SSD_END) and stores the result compactly in deploy/private.js; the server returns the rows for the pupil's own local date with a mark. The page never holds them before marking.
D64 · A date column in the expected rows is stored as a day offset only when that gives fewer distinct values over the range (so 2017-3's fixed dates stay plain text).
D65 · The leak audit's two warnings are not leaks: 2016-2 '13:00'/'15:00' and 2025-b '60' are the question's own words and the unit a pupil must convert.
D66 · The Result card after marking compares values only (numbers normalised), in order only when the question sorts. When the pupil's column count differs from the expected rows' the card shows both grids with "Different rows", which is true: the rows differ.
D67 · Attempts are stored as [minutes, total, script] per part; the first and best scripts are always kept; middle scripts are dropped once a part's record passes 8,000 bytes. The staff drawer re-marks the stored scripts on the server to show each verdict.
D68 · The private Code.gs reaches the Apps Script editor encrypted: AES-256-GCM with a random key kept only in "Claude Work/A2 SSD Platform/deploy/" (mode 600). The ciphertext alone sits for minutes on a throwaway branch a2-deploy-bundle of the public repo; the editor tab fetches it, decrypts it in the page with crypto.subtle and sets the editor text; the branch is then deleted. The public Index.html is committed at a2-ssd/server/Index.html.
D69 · The first door reads "Learn it first" (§12a, which his look approved) rather than SPEC §3.6's "Show me how first". Its sub-line says the lesson is on a different database and the question's answer is not shown; a written-answer lesson says "what this part asks about" instead of "the SQL this part needs".
D70 · The fourth beat is "Another question" everywhere (ruling 5). The paper's part list shows "Another question t / of" where SPEC §3.4 had "Proved".
D71 · The paper evaluation lists one "I can" line per group of skills the paper's parts use (CREATE, ALTER, INSERT, UPDATE, joins and fields, WHERE tests, grouping and totals, sorting, dates, written design answers), at most five, in the order the parts first need them. The record stores group → choice.
D72 · Pupil text says "your teacher", never a name, so the site works for any teacher's class.
D73 · Strings added beyond SPEC §3 and the prototype, each for a state SPEC did not draw: a locked paper reached by its link (paper.lockedHere, sys.locked); Another question before a first mark (aq.after); the evaluation before the last part (ev.notYet); the DATA tab captions and the no-rows line; the answer-kind prompts (cloze, short, rows headers, blank labels); "Marking…"; the expected-rows note; staff move, copy, owner-only, clear-my-record and drawer labels.
D74 · D18 is built: pack-content writes part.hides ({table} for a CREATE, {table, col} for ALTER … ADD) and the DATA tab leaves that table or column out.
D75 · The page is one inlined Index.html (style, body, every script) so Apps Script serves a single file; sql.js is loaded from cdnjs first and from the repo's github.io vendor copy if cdnjs is blocked.
D76 · Pupil records live in Script Properties (one per pupil per class, scripts per part separately); when the store nears its limit the owner's staff visit moves the oldest finished papers' scripts to the owner's "A2 SSD - Archive" Sheet. The served page never touches a Sheet.

D78 · A local dev harness (tools/dev-server.js) runs the real built Code.gs in Node with an in-memory property store, so every gate walks the exact server that deploys.
D79 · "This part needs" on The question lists the lesson's own step names, so the words match what the lesson then shows.
D80 · Another question's worked answer uses the same "Examiner's answer" card and strings as the exam part, with the numbered walk-through under it.
D81 · The DATA tab matches practice tables to design tables by name ignoring case, spaces and punctuation; the practice rows' 'now' and the pupil's GETDATE() both mean the pupil's own date.
D82 · Opening The question or The lesson before a first mark records the door as Learn it first; the rail never lets a pupil slip into the lesson and still be counted unaided.
D83 · How did it go? asks about at most five skill groups, taken from the paper's parts in order of first need; any written-answer part adds the "explain in words" line.
D84 · The door choice and the lesson's progress are kept per pupil per part in her own user storage (with a local copy), so they follow her to another machine.
D85 · The last verdict for each part is kept in the browser so a returning pupil sees her marks at once; the server's record is still what counts.
D86 · Staff Live cells show the first total for the parts marked so far, with "n of m parts" while a paper is unfinished; the drawer loads attempts only when asked.
D87 · No cold-read checklist existed for this platform, so each packet carries its own COLD_READ_CHECKLIST.md (closed questions: plain words, one action per line, shows what it asks).
D88 · Gate screenshots (probes/*.png) are gitignored; the text reports are committed so the repo stays small.
D89 · The encrypted deploy bundle is fetched by commit sha, never by branch name (the raw CDN served a stale copy by branch); the throwaway branch was deleted after the deploy.
D90 · The web app's execute-as and access come from the manifest (USER_ACCESSING, DOMAIN), so the deploy dialog opened already set and was checked, not changed.
D91 · G3 reads the class and papers that G5 sets up in the dev store, so the gate order is G5 then G3. A store reset between them empties every G3 page.
D92 · Sit walks drive the live site only in the foreground Chrome tab. The browser tool's clicks do not reach the Apps Script frame in a background tab, so walk 1 was void.
